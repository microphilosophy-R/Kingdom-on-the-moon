# 优化器决策改进方案（PROFIT_BASE=1）

## 1. 摘要

当前优化器 `planFacilityAutomation`（[automation.ts](file:///c:/Kingdom%20on%20the%20moon/src/economy/automation.ts)）的经济基础（配方、资源权重、成本公式）已经合理，问题集中在**决策评分逻辑**：评分由「价值加权 + 多个 ad-hoc 加成」拼装，存在几处会系统性诱导错误决策的缺陷。

本方案不改配方、不改 `resourceWeights`、不改成本公式，只重构优化器的**评分与约束**，目标：

1. 让维生（水/氧/生物质）安全成为**前置硬约束**，而不是等到跌破债务上限才拦截。
2. 修正 D/R 的「Math.max 兜底」导致亏损项目反复上马。
3. 修正成本摊销期过长导致过度扩建。
4. 消除住房「一刀切锁死」与「后期胜利硬编码」等 ad-hoc 逻辑。

预期效果（PROFIT_BASE=1 下复测 1000 日模拟）：维生紧张天数显著下降、人口不再冲高回落、星舰推进与实际材料就绪度挂钩。

---

## 2. 当前状态分析（决策缺陷清单）

所有行号基于当前 [automation.ts](file:///c:/Kingdom%20on%20the%20moon/src/economy/automation.ts)。

### 缺陷 A：D/R 用 `Math.max` 兜底评分（L415）

```ts
const weightedGain = Math.max(normalGain, projectSinkGain(id, current.level, workingResources, reserveFloors))
```

`projectSinkGain`（L41-L63）只看「盈余价值 / 阶段投入」比例，最高给 300 分，**无视设施净产出是否为负**。导致 D（星舰坞）和 R（生态环）即使每天净消耗大量物资，只要有盈余就被拉到高分反复扩建。

### 缺陷 B：成本摊销期过长（L422）

```ts
const weightedCost = (weightedValue(cost, weights) + tradePremium) / horizon + ...
```

`horizon` 来自 `input.capitalHorizonYears ?? 5`，而模拟循环传入 `360`（[simulation.test.ts](file:///c:/Kingdom%20on%20the%20moon/tests/simulation.test.ts) L411）。成本被摊薄到 360 天，每天成本趋近于 0，导致扩建「看起来极便宜」，是 K 一路扩到 13 级、工业/住房过度扩张的根源之一。

### 缺陷 C：维生安全只有「债务上限」兜底，没有前瞻约束（L405-L411）

```ts
const breachesDebtLimit = resourceOrder.some(key => {
  const limit = resourceDebtLimits[key]
  return limit !== undefined && (projectedResources[key] ?? 0) < limit
})
```

这里只检查「施工后是否跌破债务上限（如 water -1000）」。而水/氧/生物质的**储备线**（reserveFloors：water 8 / oxygen 10 / biomass 8）才是维生健康的边界。当前逻辑允许扩建把维生长期压在储备线以下，只拦 -1000 的极端情况，是「紧张天数高」的直接原因。

### 缺陷 D：住房扩建被 `lifeSupportRatio < 1` 一刀切锁死（L390）

```ts
if ((input.population?.lifeSupportRatio ?? 1) < 1) return null
```

维生紧张恰恰需要先补维生设施，而住房扩建被整体锁死，形成「越缺越不建」；同时住房的评分没有把「新增人口的维生消耗」计入，导致住房在维生充裕时又被过度扩建。

### 缺陷 E：后期胜利推进硬编码 + 举债反馈（L282-L310）

`overstockTechnologyBonus` 奖励合金/月壤/货币盈余（这些盈余是信贷采购堆出来的），`lateGameVictoryBonus` 再给 D 固定 `+40`，形成「举债买材料 → 显示超储 → 加分成 → 扩 D → 更缺」的循环。

### 缺陷 F：赤字激励重复计分（L377-L403 与 L421）

`strategicBonus`（资源低于储备线时的 ±加成）与 `deficitRelief`（`deficitPremium` 差值）功能重叠，都是「赤字激励」，叠加后权重不可控。

## 3. 改进方案

### P0-1：D/R 评分从「兜底」改为「加法」（修缺陷 A）

**文件**：[automation.ts](file:///c:/Kingdom%20on%20the%20moon/src/economy/automation.ts) L415

**改法**：

```ts
const weightedGain = normalGain + projectSinkGain(id, current.level, workingResources, reserveFloors)
```

让蓄水池加分成为「锦上添花」，而不是把负的 `normalGain` 强行抬成正分。D/R 在净产出为负时不再因盈余而获得虚高评分。

### P0-2：成本摊销改为固定回收期（修缺陷 B）

**文件**：[automation.ts](file:///c:/Kingdom%20on%20the%20moon/src/economy/automation.ts) L422

**改法**：新增模块级常量，替换对 `horizon` 的依赖：

```ts
/** 扩建成本摊销天数：按约 3 个王月（90 御日）回收，避免 horizon=360 把成本摊薄到趋近 0。 */
const COST_AMORTIZATION_DAYS = 90
```

```ts
const weightedCost = (weightedValue(cost, weights) + tradePremium) / COST_AMORTIZATION_DAYS + Math.max(0, deficitPremiumDelta)
```

同时保留 `horizon` 用于人口迁移投影（L395）等其它语义，仅成本摊销这一处改用固定常量。

### P0-3：维生安全前瞻约束（修缺陷 C，核心）

**文件**：[automation.ts](file:///c:/Kingdom%20on%20the%20moon/src/economy/automation.ts) L405-L426

**改法**：在 `nextYearProjection` 计算之后、`score` 计算之前，加入维生安全惩罚：

```ts
/** 维生跌破储备线的惩罚系数：扩建若让水/氧/生物质一年内跌破储备线，重罚。 */
const LIFE_SUPPORT_SAFETY_PENALTY = 6

const nextYearProjection = applyBundle(projectedResources, upgradedNet)
let lifeSupportSafetyPenalty = 0
for (const key of ['water', 'oxygen', 'biomass'] as ResourceKey[]) {
  const projected = nextYearProjection[key] ?? 0
  const floor = reserveFloors[key] ?? 0
  if (projected < floor) {
    lifeSupportSafetyPenalty += (floor - projected) * weights[key] * LIFE_SUPPORT_SAFETY_PENALTY
  }
}
```

然后 `score -= lifeSupportSafetyPenalty`。

**作用**：扩建若会恶化维生（如消耗水的工业、过度住房），会被重罚；扩建维生设施（B/P/C1）则会提升 `nextYearProjection` 的维生库存、变相加分。这是把维生安全从「-1000 债务上限兜底」提前到「储备线」的关键。

> 需要补充 `import type { ResourceKey }`（若当前未导入；`resourceOrder` 已可用，也可用 `resourceOrder.filter(...)` 避免新增类型导入）。

### P1-4：住房扩建维生耦合（修缺陷 D）

**文件**：[automation.ts](file:///c:/Kingdom%20on%20the%20moon/src/economy/automation.ts) L389-L403

**改法**：
1. 删除 `if ((input.population?.lifeSupportRatio ?? 1) < 1) return null` 的一刀切锁死。
2. 在住房分支里，把「新增人口带来的维生消耗」计入 `annualGain`：新增人口 × 每居民 water/oxygen/biomass 消耗，作为负向收益，让住房扩建的评分自然反映维生成本，而不是锁死。

具体新增人口按 `potentialMigrants`（已计算）折算，复用 [population.ts](file:///c:/Kingdom%20on%20the%20moon/src/economy/population.ts) 里 K/H/M 每居民的 `method.input`（water/oxygen/biomass）。

### P1-5：后期胜利推进去硬编码（修缺陷 E）

**文件**：[automation.ts](file:///c:/Kingdom%20on%20the%20moon/src/economy/automation.ts) L282-L310

**改法**：`lateGameVictoryBonus` 不再给 D 固定 `+40`，改为基于「星舰当前阶段材料就绪度」：

```ts
// 星舰推进加分 = 当前阶段材料盈余价值 / 阶段总投入价值（与 projectSinkGain 同口径）
```

让 D 的扩建评分与实际材料储备挂钩，材料不够时不强行推 D；`overstockTechnologyBonus` 仅保留对科技/后期的温和加成，不再作为 D 的乘数。

### P1-6：统一赤字激励（修缺陷 F）

**文件**：[automation.ts](file:///c:/Kingdom%20on%20the%20moon/src/economy/automation.ts) L377-L403 与 L421

**改法**：删除 `strategicBonus` 里基于 `workingResources[key] < reserveFloors[key]` 的 ±加成（L380-L388），统一由 P0-3 的 `lifeSupportSafetyPenalty` 与已有的 `deficitRelief`（`deficitPremium` 差值）承担赤字激励，避免重复计分。

## 4. 假设与决策

- **不改** `resourceWeights`、配方、`projectFacilityCost`、`resourceDebtLimits`、`reserveFloors`。用户已确认「经济基础合理」。
- `COST_AMORTIZATION_DAYS = 90`、`LIFE_SUPPORT_SAFETY_PENALTY = 6` 为初值，若复测后过度保守/激进，可再调，但本方案先固定这两值以保证可执行。
- P0（1/2/3）为本次必做核心；P1（4/5/6）为配套改善，建议一并落地以消除遗留 ad-hoc 逻辑。
- 保留 `rateStaffingFacilities` 与 `rebalanceStaffing` 现有口径（上一轮已统一），本次不再改动 staffing 评分结构。

## 5. 验证步骤

1. `npx tsc -b` 通过。
2. `npx vitest run tests/economy.test.ts tests/events.test.ts tests/gameContentAgent.test.ts` 全绿（如 `evaluate` 行为变化导致既有断言失效，按「以代码为准」同步更新期望值）。
3. `$env:PROFIT_BASE='1'; npm run simulate`（或 `npx vitest run tests/simulation.test.ts --reporter=verbose`），对比改造前后：
   - 各难度维生紧张天数（`strainedDays`）应显著下降；
   - 人口峰值回落幅度减小、终值更接近稳定；
   - `started` 项目数不再无节制（K 不再一路冲 13 级）；
   - 星舰 `shipWinDay` 是否合理推进（材料就绪时完成，未就绪时不强行完成）。
4. 如需对比，可再跑 `$env:PROFIT_BASE='0.9'`，观察维生约束在低利润基准下是否同样有效。
